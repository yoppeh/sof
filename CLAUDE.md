# sof

A collection of c libraries, one per directory. Libraries build on each
other rather than carrying copies of each other's files: _sof_hashmap/_ uses
_sof_hash.c_ and _sof_hash.h_ from _../sof_hash/_.

_sof_hash/_, _sof_hashmap/_ and _sof_rbtree/_ are the reference libraries, and every
library follows the conventions below. A new library is written to them from
the start, added to `MODULES` in the root _Makefile_ and listed in the root
_README.md_. The project is new, so changing a library's API to fit the
conventions is fine; there are no users to break.

The collection serves two purposes. It is a reference implementation: a
reader can take one library's directory, with those of the libraries it
uses, drop the code into their own project, and have the documentation and
a demo of it in use alongside. And it is one library: the root _Makefile_
builds every library into a single static library, _build/libsof.a_, and
installs it with the headers, for use as a unit, on any operating system.

The libraries are also the portable components of _laf_ (Linux Application
Frameworks, in _../laf_), a separate project that builds Linux-only shared
libraries over them. Nothing here depends on laf, and nothing here is
Linux-specific.

## Layout of a library

    name/
        name.h       public declarations, fully documented
        name.c       the implementation
        test.c       the tests, a program of their own (see Tests)
        bench.c      optional: a benchmark, when speed is the point
        demo/        the library's demo, a program (see Programs)
        Makefile
        README.md
        LICENSE      MIT, Warren Mann

The test harness every library's tests share is in the root _test/_
directory: _test.h_ and _test.mk_ (see Tests), and _test_json.h_, an RFC 8259
JSON checker for tests that write or read JSON.

Libraries have no dot files of their own: no _.gitignore_, _.aember/_ or
editor state. The root _.gitignore_ covers every library, including the
_test_ and _bench_ executables, the demo programs and _build/_; add a rule
there if a library or demo builds something else.

A library that uses another includes its header by name (`#include "sof_hash.h"`)
and its Makefile finds it with `-I../sof_hash`, so the same source builds when
the files are copied flat into another project. The Makefile compiles the
other library's _.c_ files into its own directory (see Makefile below), so
libraries never write into each other's directories and `make -j` is safe.
The README names the libraries it uses.

All code here, whether library, test, program or benchmark, uses the
collection's own APIs wherever one does the job, rather than the c library
or code of its own: memory through _sof_alloc_, command line options through
_sof_copt_, configuration files through _sof_config_, logging through _sof_log_,
hashing through _sof_hash_, maps through _sof_hashmap_, ordered sets through
_sof_rbtree_, debug tracing through _sof_debug_, and so on for each library as it
is brought in line. Before writing a helper, check whether a library here
already provides it. A library that would make a needless dependency (a
tiny library pulling in a big one for one call) can do without, but say
why in a comment.

Vendored third-party code (such as _rapidhash.h_) is kept unchanged under its
own license, is included only by the _.c_ file that needs it, and is named in
the README. Beyond the libraries in this collection, a library needs nothing
but the c standard library unless it can't reasonably avoid it, and the
README says so if it does.

A table too large or exact to write by hand (_sof_real_'s powers of ten) is
generated by a script kept in the library's directory (_gen_table.py_), with
exact arithmetic, into a header named _*_internal.h_ so `make install`
leaves it out. The README says how to regenerate it, and a test checks
entries against values the test computes itself.

A fast path through processor instructions or compiler builtins
(_sof_digest_'s SHA-256 instructions, `__int128` in _sof_random_ and
_sof_real_, the GNU builtins in _sof_bit_) always has a portable path in
plain c beside it. It is chosen at compile time from the compiler's
feature macros, or at run time where the instructions may be missing (x86's
SHA-NI, with `__attribute__((target))` and `__builtin_cpu_supports()`). A
macro forces the portable path (`SOF_DIGEST_PORTABLE`,
`SOF_RANDOM_NO_BUILTINS`, `SOF_BIT_NO_BUILTINS`), and the library builds a
test program with it (see Tests), so both paths are tested on every machine.
Keep a fast path only if it measures faster; the README gives the numbers.

## API conventions

**Utility libraries.** The conventions below are written for data structures
and algorithms. Utility libraries (_sof_bit_, _sof_debug_, _sof_hash_,
_sof_log_) follow them where they apply and have more freedom where they
don't: a library with no state needs no main struct, no `init`/`free` pair
and no error enum; one that works on values rather than pointers has no
**NULL** cases; and one made of `static inline` functions can be a header
with no _name.c_. Its own types, such as _sof_bit_'s word, need not be
`uint64_t`. The header and README say what it does instead.

**Names.** Everything public is prefixed with the library's name:
`sof_hashmap_insert()`, `SOF_HASHMAP_OK`. Types are `snake_case_t`, and the
`typedef` tag repeats the name (`typedef struct sof_rbtree_t { ... } sof_rbtree_t;`).
Callback types end in `_func_t` (`sof_rbtree_key_compare_func_t`,
`sof_hashmap_element_delete_func_t`, `sof_hashmap_traverse_func_t`). Older libraries
use `_s`/`_e`/`_f` suffixes; rename them.

**The caller owns the main struct.** The application provides the `name_t`
(on the stack, in another struct or on the heap) and sets it up with
`name_init(name_t *, ...)`, which returns an error code. `name_free()`
releases what the library allocated and leaves the struct empty, but never
frees the struct itself. There is no `name_new()` returning a heap pointer,
and no `_cleanup()` or `_exit()`: the pair is `init`/`free`. `name_clear()`
empties without freeing, when that makes sense.

**Errors.** Each library has its own enum, in this order:

    typedef enum name_error_t {
        NAME_OK = 0,
        NAME_NO_MEM,
        NAME_NO_MATCH,
        NAME_ERROR,
    } name_error_t;

with codes added after these only when callers need to tell more cases apart.
Functions that find or create something return a pointer, with **NULL** for
failure, and take an optional `int *created` where insert-or-find needs it.

**NULL and dead objects are safe.** Every function accepts a **NULL** main
struct (and, where it applies, a **NULL** key), and a struct that was freed or
whose init failed. That struct is simply empty: lookups find nothing and
inserts fail until it is initialized again. Pointer-returning functions return
**NULL**, traversals return **-1**, and the rest return `NAME_ERROR`. Hashing
functions treat **NULL** data as empty. The header and README both say what
each function does with these.

**Callbacks take a `void *ctx`.** `init` takes a _ctx_ that is passed to
every stored callback (compare, hash, delete...), and each traversal takes its
own _ctx_ for its callback, so applications never need globals. A delete
callback (`del_func`) receives each element or node just before it is
removed, by every function that removes, so the application can free what it
owns; it must not call back into the structure. Traversal callbacks return
**0** to continue, or non-zero to stop, and that value is returned by the
traversal. Where a callback-free loop is natural, there is one too
(`sof_rbtree_next()`, `sof_hashmap_next(map, &position)`).

**Elements/nodes** expose a `key` and a `void *data` that the library never
reads or writes. Structure fields can be read by the application but not
changed; the header says so. If pointers to elements can move (as in
_sof_hashmap_), the header and README say when.

**Functions that only read take `const`.** A function that doesn't change the
main struct (lookups, `next`, traversals, sizes, peeks) takes a
`const name_t *`, and the same goes for any other argument it only reads, so
callers holding a `const` pointer never need a cast. These are the functions
the README's Threading section lists as only reading.

**Memory comes from a `sof_alloc_t`.** A library that allocates takes a
`const sof_alloc_t *alloc` as the last argument of `init` (**NULL** for the
standard functions), returns `NAME_ERROR` if `sof_alloc_valid()` rejects it,
keeps a copy, and allocates and frees only through the _sof_alloc.h_ helpers,
never `malloc()` or `free()` directly. Every `sof_alloc_free()` gets the exact
size the block was allocated with, so a block's size must be known or
recomputable when it is freed (array capacities, `strlen() + 1`). Callbacks
that allocate for the library (such as _sof_hashmap_'s key `copy` and `free`) are
passed the allocator. The tests use the test allocator in _test/test.h_ to
fail each allocation in turn and check that nothing leaks and every size is
right. The Makefile builds _../sof_alloc/sof_alloc.c_ like any other library's file.

**No global state and no locking.** The library has no globals, so separate
instances work on separate threads. Shared instances need an application
lock; the README's Threading section says which functions only read.

**Code style.** 4-space indents, braces on every `if`, `static` prototypes for
internal helpers listed at the top of the _.c_ file, public functions defined
in alphabetical order. Integer types from `<stdint.h>`/`<stddef.h>`: `size_t`
for counts and lengths, `uint64_t` for hashes and bit fields.

**Doxygen comments.** Every file starts with:

    /**
     * @file name.h
     * @author Warren Mann (warren@nonvol.io)
     * @brief One line.
     * @details Optional paragraph.
     * @version 0.0.1
     * @date YYYY-MM-DD
     * @copyright Copyright (c) 2026
     */

Every public declaration in the header has `@brief`, and `@details`,
`@param` and `@return` where they add something. Short internal comments use
`/// @brief`. Include guards are `NAME_H` (not `_NAME_H`), closed with
`#endif // NAME_H`. Public functions are declared `extern`.

## Tests

A library's tests are a program of their own, _test_, built by the
library's Makefile from _test.c_ in its directory and the library's
objects, and run from there: `make check` builds and runs them, as does
`make check-name` at the root. _test.c_ includes the library's headers by
name, then `#include "test.h"`, the harness in the root _test/_, which the
Makefile finds with `-I../test` (added by _test.mk_):

    #define CHECK(cond)  /* on failure: print "FAILED\n    file:line: cond", count it, return */
    void run(const char *name, void (*test)(void));  /* prints "name... " then "ok" */
    uint64_t next_random(uint64_t *state);           /* seeded xorshift64* */
    int test_report(void);  /* main()'s: prints "all tests passed" or "N test(s) failed" */

They are all `static` in _test.h_, so there is nothing else to compile or
link. Each test is a `static void` function; `main()` prints the library's
name and a colon, is a list of `run("what is tested", test_function);`
lines, and returns `test_report()`. The program takes no arguments. If a test
needs a second source file (_sof_copt_'s, to show options merging from two
object files), it is named _test_\*.c_, as _test_module.c_ is.

The Makefile sets `TESTS` to its test programs, usually just `test`, builds
them in `all`, removes them in `clean`, and ends with
`include ../test/test.mk`, which gives it `check`, `memcheck` and `sanitize`
(see _test/test.mk_). Test objects are compiled, and the programs linked,
with _-pthread_, since some tests use threads; the library itself isn't. A
library tested in more than one build has a test program per build in
`TESTS`, with the objects that differ named apart: _sof_log_ builds
_test-threaded_ too, with _sof_log.c_ and _test.c_ compiled with
`SOF_LOG_THREADED`, _sof_bit_ builds _test-uint8_ and _test-uint32_
with other word types, and a library with a fast path builds
_test-portable_ with the macro that forces the portable one. A library
whose tests need valgrind suppressions (_sof_regex_'s, for PCRE2's JIT code)
sets `VALGRIND_FLAGS = --suppressions=valgrind.supp` before including
_test.mk_. Tests are deterministic: random data comes from
`next_random()` with a fixed seed, never `rand()` or the time. Cover every function, the
**NULL** and freed-struct cases, callbacks being called the right number of
times (count them through _ctx_), and early stops in traversals.

Run the tests on _morbius_ as well as locally. It is an Arch Linux machine
with an Intel i9, so it covers Linux, x86-64 and real gcc, where this Mac
covers macOS, arm64 and clang. The project is also at
_morbius:/home/warren/dev/sof_. Copy the project across with rsync, which
skips _.git/_ and whatever _.gitignore_ lists, then run the tests there:

    rsync -a --exclude .git --filter=':- .gitignore' ./ morbius:/home/warren/dev/capi/
    ssh morbius 'cd /home/warren/dev/capi && make check'

rsync doesn't delete files on _morbius_ that were removed here; add
`--delete` when a file has been deleted or renamed.

On GitHub, _.github/workflows/ci.yml_ runs `make`, `make check`, `make
sanitize` and `make lib` on Linux (gcc and clang) and macOS, and `make
memcheck` on Linux, on every push; keep it working when the build changes.
Windows isn't a target.

Two more Arch Linux machines take the same commands: _davros_, an AMD Ryzen 9
5950X, and _dalek_, a Ryzen 5 5600X, neither with valgrind. They have clang
as well as gcc, so `make CC=clang check sanitize` there tests a second
compiler on Linux, and _davros_ gives benchmarks a third processor beside
the M4 and the i9. Use a directory of your own on them (and on _morbius_)
when other work may be running, and remove it after.

A library isn't done until `make sanitize` passes on both machines and
`make memcheck` passes on _morbius_ (valgrind doesn't run on macOS), as in:

    make sanitize-sof_config
    ssh morbius 'cd /home/warren/dev/capi && make sanitize-sof_config memcheck-sof_config'

`sanitize` builds with AddressSanitizer and UndefinedBehaviorSanitizer (and
so LeakSanitizer on Linux) and removes the tests and the library's objects
before and after; `memcheck` runs the ordinary optimized tests under
valgrind, which also catches reads of memory that was never set. At the
root, `check`, `sanitize` and `memcheck` run the same in every library, or
those given as `run="name..."`.

Large data files shared by tests, programs and benchmarks live in the root
_test-data/_ directory, and programs open them as _../test-data/name_, since
they run from their library's directory. _test-data/words.txt_ is a list of
263,533 words, for when a program needs many distinct keys.
_test-data/shakespeare.txt_ is the complete works of Shakespeare from Project
Gutenberg (5.6 MB of UTF-8, about 970,000 words, CRLF line endings), for when
it needs real text, in which words and phrases repeat as they do in writing.
_test-data/README.md_ names each file's source and license; add a line there
for any new file, and keep third-party files unchanged. Prefer generated data
where it does the job.

## Benchmarks

A library's demo, in its _demo/_ directory (see Programs), shows it in
use. A benchmark compares the library with simple
alternatives, reports the best of several runs, and keeps the compiler from
discarding results (a `volatile` sink). It has the usual file header, with
the usage line in `@details`, and is documented in the README. Benchmarks,
programs and any other code here that takes options read them with
_sof_copt_ (as _sof_hashmap/demo/main.c_ does), never `getopt`: the Makefile
builds _../sof_copt/sof_copt.c_ like any other library's file, and the
README names sof_copt as used by the benchmark only.

## Makefile

Copy _sof_hash/Makefile_ and change the names. In order:

1. A header comment listing every target (`all`, `clean`, then the rest
   alphabetically) and the variables `CC`, `CFLAGS`, `debug=1` and
   `LDFLAGS`, each with a line saying what it does.
2. The flag block, unchanged between libraries:

       ifeq ($(origin CC),default)
       CC = gcc
       endif
       override CFLAGS += -Wall
       ifdef debug
       override CFLAGS += -ggdb -D DEBUG
       else
       override CFLAGS += -O3
       endif

   `override` makes these add to a `CFLAGS` or `LDFLAGS` given on the command
   line, which would otherwise replace them, dropping `-Wall` and the `-I`
   flags.

3. `TESTS = test`, `.PHONY: all clean demo`, then `all:` compiling the
   library and building the tests, any benchmark and the demo (a header-only
   library checks that its header compiles alone, with `-fsyntax-only`),
   `clean` removing `$(TESTS)`, the other executables and `*.o` and running
   `$(MAKE) -C demo clean`, and `demo:` running `$(MAKE) -C demo`.
4. A rule per executable, `$(CC) $(LDFLAGS) $^ -o $@`; the tests'
   `$(CC) $(LDFLAGS) -pthread $^ -o $@`, adding any system library they
   need. Benchmarks and programs are stripped unless `debug` is set; the
   tests never are.
5. Object rules: one for any file with extra dependencies (such as
   `sof_hash.o: sof_hash.c sof_hash.h rapidhash.h`), one per file taken from another
   library (`sof_hash.o: ../sof_hash/sof_hash.c ../sof_hash/sof_hash.h ../sof_hash/rapidhash.h`),
   then `test.o: test.c name.h ../test/test.h`, compiled with `-pthread`,
   then `%.o: %.c name.h`. A
   library that uses another adds `override CFLAGS += -I../other` after the flag
   block, for the library, its tests and its benchmark alike.
6. `include ../test/test.mk`, last, for `check`, `memcheck` and `sanitize`.

The root _Makefile_ runs `all`, `clean`, `check`, `sanitize` and `memcheck`
in every directory in `MODULES`, and has `name`, `clean-name`,
`check-name`, `sanitize-name` and `memcheck-name` targets for one library,
and `test`, the same as `check`, for tools (such as Aember) that run
`make test`. It also has `lib`, `install` and `uninstall` for the single
library: `lib` compiles the _.c_ files of every library in `MODULES` (but
benchmarks, tests and demos) into _build/_ and archives them as
_build/libsof.a_, and `install` copies it and the public headers (all but
_*_internal.h_) to `PREFIX`. There is no shared library. A new library's
_.c_ files are found by `lib` itself; any system library it needs to link
with is named in the root _README.md_'s Building section. Variables given on the command line reach the library Makefiles
through make itself. Keep both working with GNU Make 3.81, which is what macOS
ships.

## README.md

Each library's README follows this order:

1. `# name`, then a one-line description ending in "in c." (lowercase c).
2. An overview paragraph: the main type, that the application provides it and
   sets it up with `name_init()`, then each function in a sentence, in the
   order a program would use them. A paragraph on how it works inside, if
   that affects the caller (probing and growth for _sof_hashmap_).
3. Which files hold what: the tests (_test.c_, with the harness in
   _../test/_), any benchmark,
   the library's demo in _demo/_ and other libraries' demos that make
   notable use of it, declarations, any vendored code and its
   license, and what the library depends on, including other libraries in
   this collection.
4. An indented code sample of typical use, with short trailing comments.
5. `## Building`: an indented block of `make`, `make check`,
   `make sanitize`, `make memcheck`, `make debug=1` and running any
   benchmark, each with a comment, then a paragraph on what the tests
   cover, then how to use the library in another project (which files to
   copy, including those of any library it uses; the tests need
   _../test/test.h_ and _../test/test.mk_ as well).
6. `## Benchmark`, if there is one: its usage line, its options
   as a list, an example, and for a benchmark, a table of results and the
   machine they came from.
7. `## Keys`, or another section, for anything the functions depend on that
   is best explained once (_sof_hashmap_'s key callbacks).
8. `## Functions`: for each function, its full prototype in backticks on one
   line, then a blank line, then a paragraph of its own (not run on from the
   prototype's line) saying what it does, what each
   argument means, and what it returns in every case. Then a closing
   paragraph on **NULL** and freed-struct handling.
9. `## Types`: each public type as an indented c block, followed by what the
   application may and may not do with it.
10. `## Threading`: what is safe concurrently, which functions only read, and
    what to watch for with a reader-writer lock.

Formatting: function and type names in backticks; argument names and file
names in _italics_; constants such as **NULL**, **0** and **SOF_HASHMAP_OK** in
bold. Code blocks are indented four spaces, not fenced. Plain, direct
sentences; no marketing.

The root _README.md_ lists every library with a one-line description and a
link to its directory, lists the demos with the libraries each uses, and
has the same Building section for the whole project, including the single
library.

## Programs

A library's demo is a real program, named for what it does, in the
library's _demo/_ directory (_sof_hashmap/demo/_ is _ngram_, an n-gram
finder). Every library has exactly one. A demo shows its library at work and
may use any other library here. Demos follow the rules above for code,
Makefiles and READMEs, with paths one level deeper (`-I../../sof_hash`),
and have no tests. The library's Makefile builds the demo: it has a `demo`
target, `$(MAKE) -C demo`, which `all` depends on, and `clean` runs
`$(MAKE) -C demo clean`. The root _Makefile_ doesn't list the demos, since
building a library builds its demo. A demo that uses another demo's code reaches it by path
(_sof_random/demo/_ uses _../../sof_hashmap/demo/ngram.c_), and its README
says so. The root _README.md_ lists each demo with the libraries it uses;
keep it up to date when a demo or library changes, and give a new library a
demo of its own.
